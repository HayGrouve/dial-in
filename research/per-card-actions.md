# Per-card secondary actions in a mobile PWA

Research for [#8](https://github.com/HayGrouve/dial-in/issues/8), a child of the map [#6](https://github.com/HayGrouve/dial-in/issues/6) ("Make finishing and restocking a bag easy to reach").

**Question:** which patterns for a per-item secondary action (swipe-to-reveal, long-press / context menu, a visible "…" overflow button, an inline button) work reliably on iOS Safari / installed iOS PWA and Android Chrome, given Dial In's home screen layout?

**Scope:** trade-offs only. Picking the design is the home-screen prototype ticket's job.

Sources were checked on 2026-10-26. Browser support comes from [MDN browser-compat-data](https://github.com/mdn/browser-compat-data) (`main`). Engine behaviour comes from WebKit/Chromium source and bug trackers.

## The surfaces in question (`src/pages/Home.tsx`)

| Surface | Markup today | Gesture already owned by the platform |
| --- | --- | --- |
| **Shelf** cards | `<li class="snap-start">` in a `<ul class="flex snap-x snap-mandatory overflow-x-auto">`. Each card is one wouter `<Link>` (an `<a>`) wrapping a `BagPhoto`, name, roaster and settings line. Width is `42vw`, capped at 180px. | Horizontal pan scrolls the row; vertical pan scrolls the page. |
| Up Next card | A `<section class="card">` holding two sibling links: the coffee link and "Log another …". | Vertical pan scrolls the page. |
| Finished rows | Full-width `<Link>` rows (`rounded-full px-4 py-3`) in a folded list. | Vertical pan scrolls the page. |

Every item is a single `<a>`, so any visible per-item control means restructuring the markup (see [Markup constraint](#markup-constraint-no-buttons-inside-links)).

## Findings by pattern

### 1. Swipe-to-reveal

- **It conflicts directly with the shelf row.** A horizontal swipe on a shelf card is already the gesture that scrolls the row. To claim it, script would need `touch-action: pan-y` (or `none`) on the card. When a gesture starts, the browser "intersects the `touch-action` values of the touched element and its ancestors, up to … the first containing scrolling element" ([MDN `touch-action`](https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action)). Cards fill the row, so a gesture starting on any card could no longer scroll the row. If the row keeps `pan-x`, the browser takes the gesture and fires `pointercancel` once "the pointer is then used to manipulate the viewport by panning, zooming, or scrolling" ([MDN `pointercancel`](https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event)). The script never sees the swipe. A *vertical* swipe on a card collides with page scroll in the same way. **On the shelf, swipe-to-reveal is effectively off the table.**
- **It works on full-width vertical lists (Finished rows, Up Next).** `touch-action: pan-y` on the row lets the page scroll vertically while script handles horizontal drags. Support: `touch-action` and `pan-x`/`pan-y` since Safari/iOS 13, `manipulation` since iOS 9.3 (BCD), and `pointercancel` since Safari 13 (BCD). This is the pattern Apple uses in Mail. The HIG gesture table lists Swipe as "Reveal actions and controls; dismiss views; scroll" ([HIG Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures)). Android ships it as `SwipeToDismissBox` ([Android: swipe to dismiss](https://developer.android.com/develop/ui/compose/touch-input/user-interactions/swipe-to-dismiss)).
- **Edge conflicts.** Android's system back gesture is "an inward swipe from either the left or the right edge of the screen". Native apps can opt out with `setSystemGestureExclusionRects()` ([Android gesture navigation](https://developer.android.com/develop/ui/views/touch-and-input/gestures/gesturenav)). Web content has no equivalent API, so a row swipe that starts near the screen edge goes to the OS. In an iOS Safari *tab*, edge swipes navigate history. *Not verified:* whether an installed iOS home-screen web app exposes an edge back-swipe. Check on a device during the prototype.
- **Accessibility.** Swipe is a path-based gesture, so WCAG 2.5.1 Pointer Gestures (A) requires the function to also work "with a single pointer without a path-based gesture" ([Understanding 2.5.1](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html)). If the row follows the finger like a drag, 2.5.7 Dragging Movements (AA) requires a non-dragging alternative too, and that alternative "can't exclusively rely on a path-based gesture, such as swiping" ([Understanding 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)). Swipe also does nothing for keyboard users (WCAG 2.1.1). VoiceOver takes single-finger swipes for its own navigation. A swipe only reaches the page via "double-tap and hold … until you hear three rising tones, then make the gesture" ([Apple: VoiceOver gestures](https://support.apple.com/guide/iphone/learn-voiceover-gestures-iph3e2e2281/ios)). Native iOS and Android apps expose swipe actions to screen readers as *custom actions*; Android's docs show exactly this for `SwipeToDismissBox` ([Android accessibility principles](https://developer.android.com/guide/topics/ui/accessibility/principles)). **The web has no equivalent.** The current [ARIA editor's draft](https://w3c.github.io/aria/) defines no `aria-actions` or similar. So a web swipe action always needs a visible control as well.
- **Platform guidance agrees.** Apple's accessibility guidance: "if you use a swipe gesture to dismiss a view, also make a button available so people can tap or use an assistive device" ([HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). The HIG's rule for custom gestures is that they must be "Not the only way to perform an important action" ([HIG Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures)).
- **Cost.** There is no platform primitive for this, so it means custom pointer-event code: thresholds, velocity, snapping back, cancelling on vertical scroll. It is the most bespoke of the four options.

### 2. Long-press / context menu

- **iOS does not fire `contextmenu` on touch.** BCD has `contextmenu` with `safari_ios: false`, tracked in [WebKit bug 213953](https://bugs.webkit.org/show_bug.cgi?id=213953), which has been open since 2020. The reporter notes long-press shows the magnifier instead. The event fires on iPad only with a mouse or trackpad secondary click. On iOS, a long-press therefore has to be built from pointer or touch events plus a timer, cancelled on movement or `pointercancel`.
- **Android Chrome does fire `contextmenu` on long-press.** Blink's `GestureManager::HandleGestureLongPress` ends in `SendContextMenuEventForGesture`, which dispatches a `contextmenu` event ([Chromium `gesture_manager.cc`](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/input/gesture_manager.cc)). Calling `preventDefault()` on it suppresses Chrome's own link/image menu. The same code shows long-press also feeding text selection (`selection_controller_->HandleGestureLongPress`) and, behind feature flags, touch drag-and-drop on links and images. So the two engines need different code paths.
- **iOS link previews and callouts.** The shelf cards are `<a>` elements with an image, so a touch-and-hold opens WebKit's own link preview / context menu. WebKit returns no context menu configuration when `touchCalloutEnabled` is false, i.e. when `-webkit-touch-callout: none` is set ([WebKit `WKContentViewInteraction.mm`, `continueContextMenuInteraction` and `_actionForLongPressFromPositionInformation`](https://github.com/WebKit/WebKit/blob/8b41a55153eacb8a6b9e562b60402cac69bfb579/Source/WebKit/UIProcess/ios/WKContentViewInteraction.mm)). The property is non-standard and only supported on iOS Safari (BCD: `safari_ios: 2`, desktop Safari and Chrome `false`; [MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/-webkit-touch-callout)). It also suppresses the image save callout ([WebKit bug 220642](https://bugs.webkit.org/show_bug.cgi?id=220642), where the reporter also found an extra `mousedown` firing on long-pressed `img`s with the callout disabled).
- **Text selection and loupe.** `-webkit-user-select: none` stops selection and the long-press loupe. That only works since a fix shipped in iOS 15.2 ([WebKit bug 231161](https://bugs.webkit.org/show_bug.cgi?id=231161)). A tap-then-long-press loupe "can't be disabled with CSS", only with JS, on iOS 18 ([WebKit bug 296492](https://bugs.webkit.org/show_bug.cgi?id=296492), open). The only documented JS workaround is `preventDefault()` on `touchstart`, and the WebKit thread notes it "can interfere with page scrolling". In a scroll-snap row that cost is too high.
- **No haptics on iOS.** `navigator.vibrate` is unsupported in Safari and iOS (BCD) but available on Android Chrome. So an iOS web long-press gives no tactile cue, unlike a native touch-and-hold menu.
- **Scroll.** Long-press needs no movement, so it doesn't fight horizontal or vertical scroll as long as the timer is cancelled on movement or `pointercancel`. This makes it the only *hidden* gesture that coexists with the snap row.
- **Discoverability and accessibility.** The HIG says a context menu is "hidden by default, so people might not know it's there" and says: "Always make context menu items available in the main interface, too" ([HIG Context menus](https://developer.apple.com/design/human-interface-guidelines/context-menus)). WCAG doesn't count long-press as path-based or multipoint ([Understanding 2.5.1](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html)), so 2.5.1 doesn't fail it. A timer-based long-press still has no keyboard route (2.1.1), though `contextmenu` covers the context-menu key and Shift+F10 on desktop. VoiceOver maps "Touch and hold (long press)" to a triple tap ([Apple: VoiceOver gestures](https://support.apple.com/guide/iphone/learn-voiceover-gestures-iph3e2e2281/ios)). *Not verified:* whether that synthesised press drives a JS pointer timer on iOS web content. As with swipe, long-press has to be an accelerator on top of a visible control.

### 3. Visible "…" overflow button opening a menu or sheet

- **Scroll.** A tap on a button inside a scroll-snap row only becomes a `click` if the touch didn't turn into a pan. Otherwise the browser cancels the pointer ([MDN `pointercancel`](https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event)). No gesture conflict, and it works the same on iOS and Android.
- **Discoverability.** It's visible, but the HIG warns that a More button "can also hinder discoverability … the ellipsis icon doesn't necessarily help them predict its contents". It also says "A view's primary actions need to be easily discoverable, so you don't want to hide them in a pull-down button" ([HIG Pull-down buttons](https://developer.apple.com/design/human-interface-guidelines/pull-down-buttons)). That matters if Finish/Restock is meant to be *easy to reach*: behind "…" it's two taps.
- **Accessibility.** This pattern meets every requirement directly: a real `<button>` is keyboard-reachable and gets a screen-reader name like "More actions for Ethiopia Guji". The WAI-ARIA [Menu Button pattern](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/) describes `aria-haspopup="menu"` and `aria-expanded`, with Enter/Space opening the menu and focusing the first item. With only one or two items (Finish, maybe Delete), a full ARIA menu is heavy. A small popover or bottom sheet of plain buttons is simpler.
- **Target size.** WCAG 2.5.8 (AA) requires at least 24×24 CSS px, or spacing so a 24px circle on each target doesn't intersect another ([Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). Platform guidance asks for more: "a hit region of at least 44x44 pt" ([HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)) and 48×48dp on Android ([Android: make apps more accessible](https://developer.android.com/guide/topics/ui/accessibility/apps)). WCAG 2.5.5 (AAA) asks for 44×44. A 44px hit area fits in the corner of a 150–180px shelf photo. The visible glyph can be smaller than its hit area.
- **Menu plumbing.** The Popover API (`popover`, `popovertarget`) has been fully supported on iOS since 18.3. iOS 17–18.2 is partial: no light-dismiss on outside tap, [WebKit bug 267688](https://webkit.org/b/267688) (BCD). Anchoring a menu to the button with CSS anchor positioning is newer: full support only from Safari 27 and Chrome 151, with partial support before that (BCD `position-anchor`). A bottom sheet avoids anchoring altogether. The HIG notes that "people expect a menu to appear when they choose to reveal it", while action sheets suit choices tied to an action the user just took ([HIG Action sheets](https://developer.apple.com/design/human-interface-guidelines/action-sheets)).

### 4. Inline action button (e.g. a "Finish" chip on each card, "Bought it again" on each Finished row)

- **Scroll.** Same as "…": a tap-only control, no gesture conflict.
- **Reach.** One tap. This is the most direct answer to the map's "reachable from the home screen without opening the coffee". The map has already chosen an **undo toast** over a confirm dialog, which makes a one-tap destructive-looking action acceptable.
- **Accidental taps.** The risk is mis-taps while flicking the row. A touch that becomes a pan doesn't produce a click, so the remaining risk is a deliberate-looking tap on the wrong card. The undo toast covers that.
- **Visual cost.** A labelled button on every shelf card adds clutter to a 42vw card and competes with the card's own tap target (open the coffee). An icon-only button needs an accessible name and is less self-explanatory. On Finished rows, a short trailing "Restock" text button fits the full-width layout well.
- **Accessibility.** Same as "…": native button, keyboard and screen-reader friendly, and target size is the only constraint.

### 5. (Adjacent option) Section-level edit/manage mode

The HIG notes that "In iOS and iPadOS, people must enter an edit mode before they can select table items" ([HIG Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)). A "Manage" toggle on the Shelf heading could reveal per-card Finish buttons without permanent clutter. It's tap-only and accessible, but it's a mode, and it costs an extra tap compared with inline buttons.

## Markup constraint: no buttons inside links

The HTML content model for `<a>` is "Transparent, but there must be no interactive content descendant, a element descendant, or descendant with the tabindex attribute specified" ([HTML Standard, the a element](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-a-element)). Patterns 3–5 can't place a `<button>` inside today's `ShelfCard` `<Link>` or Finished-row `<Link>`. The usual structures are:

- **Siblings:** the `<li>` (or card wrapper) holds the `<Link>` and a `<button>` side by side, with the button absolutely positioned over the photo corner or the row's trailing edge. Screen-reader order is "link, then button". The button's name has to include the coffee name, because the visual context is lost.
- **Stretched link:** the card is a plain container, the link covers it via a `::after` overlay, and the button sits above it with `z-index`.

Up Next already uses the sibling structure (coffee link plus a separate "Log another" link), so adding a control there is the cheapest change.

## Trade-off summary

| Pattern | Shelf snap row | Full-width rows (Finished, Up Next) | iOS Safari / iOS PWA | Android Chrome | Keyboard / screen reader | Discoverable | Taps to act |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Swipe-to-reveal | **Conflicts** (horizontal swipe = row scroll; vertical = page scroll) | Works with `touch-action: pan-y`. Edge swipes go to the OS. | Custom pointer code. No VoiceOver custom actions on the web. | Same. Back gesture at screen edges. | Needs a visible alternative (WCAG 2.5.1 / 2.5.7 / 2.1.1) | No | 1 swipe + 1 tap |
| Long-press menu | Coexists if the timer cancels on move / `pointercancel` | Coexists | No `contextmenu`. Needs a timer. Must set `-webkit-touch-callout: none` + `user-select: none` on the link. A tap-then-hold loupe can't be fully disabled. No haptics. | `contextmenu` fires. `preventDefault()` suppresses Chrome's link menu. | Needs a visible alternative (HIG: "make context menu items available in the main interface, too"). No keyboard route on touch. | No | hold + 1 tap |
| "…" button → menu or sheet | No conflict | No conflict | Popover API OK on iOS 18.3+. Anchoring is newer, or use a sheet. | No conflict | Native button. Menu Button pattern if it's a real menu. | Partly (HIG: ellipsis hides contents) | 2 |
| Inline button | No conflict. Adds clutter to small cards. | No conflict. Fits trailing edge of rows. | No conflict | No conflict | Native button | Yes | 1 (+ undo toast) |
| Edit / manage mode | No conflict | No conflict | No conflict | No conflict | Native buttons | Partly | 2 (mode + action) |

All tap-based patterns need the `<a>`-cannot-contain-`<button>` restructure. Targets should be at least 24×24 CSS px (WCAG AA), ideally 44pt / 48dp.

## What comparable apps do

These are first-party guidance plus a few observations; none of it is a recommendation.

- **Apple Mail (per the HIG):** list rows have swipe actions plus a touch-and-hold context menu, and the same commands are "also available in the toolbar of the message view" ([HIG Context menus](https://developer.apple.com/design/human-interface-guidelines/context-menus)). Gestures are shortcuts layered on visible controls.
- **Apple HIG on gestures:** "Use shortcut gestures to supplement standard gestures, not replace them" ([HIG Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures)).
- **Android:** swipe-to-dismiss in lists, with the same action exposed to TalkBack, Voice Access and Switch Access through `customActions` ([Android accessibility principles](https://developer.android.com/guide/topics/ui/accessibility/principles)). That accessibility route doesn't exist for web content.
- **Horizontal carousels in native apps:** items in horizontally scrolling shelves (App Store, Music, Google Play, YouTube) don't use swipe actions, because the swipe belongs to the scroll. They use touch-and-hold menus and/or a visible "…" / "⋮" button on the item. *This is an observation of current apps, not something a primary source documents.*
- **Material Design:** m3.material.io pages render client-side and couldn't be read as source text, so the Android Developers docs above (also Google, first-party) stand in for Material's guidance.

## Open items for the home-screen prototype

1. Check on a real iPhone (installed PWA) whether long-pressing a shelf card shows a link preview, and whether an edge back-swipe exists in standalone mode.
2. If long-press is used as an accelerator, check that `-webkit-touch-callout: none` + `-webkit-user-select: none` on the card is enough in practice, and that VoiceOver's triple-tap reaches it (or accept that it doesn't, since a visible control exists anyway).
3. Each surface has only one relevant action: Shelf cards and Up Next get **Finish**, Finished rows get **Restock**. Decide whether a menu is needed at all. With a single action, "…" adds a tap without saving much space; it earns its place only if more per-card actions are planned.
